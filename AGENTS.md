# AGENTS.md — `hivemind-media-player`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

`hivemind-player-protocol` turns any device into a remotely controlled OVOS media
player. It ships `HiveMindPlayerProtocol`, a `hivemind.agent.protocol` plugin that
runs the local OVOS audio stack (`ovos-audio`, OCP, optional VLC/PHAL) and exposes
it to HiveMind clients: remote controllers send OCP/audio bus messages over the
HiveMind encrypted WebSocket and this device plays them locally. It answers no
natural-language queries — its sole role is playback. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core) (AGPL; imported
only for its `AgentProtocol` base, not a runtime dependency). Related repos:
[hivemind-homeassistant](https://github.com/JarbasHiveMind/hivemind-homeassistant)
(surfaces this device as a Home Assistant media player),
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client) (the
client library used by `hivemind-player-ctl.py` and by controllers).

## Layout / build / test

- Package module: `hivemind_player_protocol/`. Tests live in `tests/` (check
  before adding — do not create a second test directory); the suite is
  end-to-end only (`tests/e2e/`), spinning up a real `hivemind-core` in-process
  and driving the plugin over a real `HiveMessageBusClient`.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]"`
- Run the suite in the foreground: `python3 -m pytest tests -q`. No `--pre`
  flag — every prerelease dependency is opted in via a floor pin in
  `pyproject.toml`.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source (the floor pins), not to work around with a pin
  downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's
  stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`
  otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries, at
  the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT human-reviewed.
  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a comment
  instead; on your own PRs, edit the body rather than piling on comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and standalone:
  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why). This repo already
  follows the pattern closely: every dependency in `pyproject.toml` carries a
  comment explaining why its floor sits on a prerelease.
- **No lockfiles, ever.** Every prerelease dependency is opted into by its floor
  pin, so a plain install resolves the right versions with no `--pre` flag.
- Everything in `pyproject.toml` (deps, metadata, version). Never install from
  git — depend on a published PyPI alpha.
- Apache-2.0. Do not add GPL/AGPL dependencies. `hivemind-core` (AGPL) is
  imported only for its `AgentProtocol` base class and stays out of the runtime
  dependency list; it is pulled in solely through the `[e2e]` test extra.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- This is a satellite app built on top of `hivemind-bus-client`, not a client
  library itself: `hivemind-player-ctl.py` (the controller CLI) and the
  in-process test topology both drive a real `HiveMessageBusClient`. Bad
  credentials failing fast (auth-reject close, no infinite reconnect) is the
  client library's contract to keep, not something to reimplement here — if you
  touch connection/auth code in this repo, verify it still delegates to that
  contract rather than adding a local retry loop around it.
- Named sessions imply a remote client: this device is a headless player with no
  local wake-word/NLU session of its own. `natural_language_query` intentionally
  yields only the end-of-query sentinel — do not "improve" it into a real
  language handler; that would contradict the device's job (see README
  Architecture section).
- Do not hardcode secrets (access keys, passwords) anywhere in code, tests, or
  example configs. `server.json.example`, `mycroft.conf.example`, and
  `.env.example` are examples only — keep them free of real credentials and
  keep any new example the same way.
- Keep the quickstart in README.md honest: it is the real, tested sequence
  (`hivemind-core add-client` → `allow-msg` grants → `hivemind-client
  set-identity` → `hivemind-core listen`). If a code change alters any step,
  update the README in the same PR rather than letting it drift.
- OCP message handling in `hivemind_player_protocol/__init__.py` mirrors the
  `Permissions` table in README.md field-for-field; if you add or rename a
  handled message, update that table in the same PR.
